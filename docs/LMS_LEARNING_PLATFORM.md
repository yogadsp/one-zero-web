# LMS Learning Platform

## Scope

The member area supports TOEFL, UTBK, CPNS, TKA, and future category records without a category-specific code change. Tryouts (`exams`), video recordings, and online classes are three independently purchasable product types. Existing transaction status and voucher activation remain the authoritative paid-access workflow.

The `students` table is the profile/access extension for a level-2 user (contact details, demographic fields, membership state, and package access). It is not a second authentication account. The legacy **Calon Siswa** navigation entry is therefore hidden; administrators manage accounts from **User**, while the profile table remains required by login, activation, transaction, and notification flows.

Each catalog item has its own title, category, price, transaction, voucher, and access entitlement. Buying a tryout does not automatically buy a new video or online class.

## Data and access model

`learning_materials.category_id` owns the product classification and `learning_materials.price` owns its independent price. `exam_id` is nullable and remains only as a legacy reference for material records that existed before the split. Material records use soft deletion and can be kept unpublished while being prepared.

A transaction references exactly one product: `exam_id` for a tryout or `learning_material_id` for a video/online class. Database triggers reject ambiguous or empty targets. A member can open protected material only when the matching transaction is `done` and its voucher is activated. Free products still pass through checkout and voucher activation, although no payment is required.

Transaction cancellation uses soft deletion. A buyer may cancel only their own `pending` or `failed` transaction; an administrator may cancel any `pending` or `failed` transaction when a correction is needed. `paid`, `done`, voucher-used, and voucher-activated records remain immutable so accounting history and learning entitlements cannot be silently removed. The transaction stores the cancelling actor and whether cancellation came from the admin or user flow. Soft-deleted invoice codes are still reserved and are never reused.

Legacy users keep access to linked material only when their activated exam transaction predates `learning_materials.standalone_since`. Future tryout purchases do not inherit the independently sold material.

The external material URL is never embedded in the package page payload. Members open an internal protected route which rechecks access before redirecting to the approved destination. Administrative create and update requests accept only HTTP or HTTPS URLs, and online classes require a start time. Voucher activation locks its transaction row, marks the voucher once, and adds the exam category to member access without duplicates. Completed and failed transactions cannot be reopened to an earlier status, and an existing voucher token is not regenerated by a repeated update.

## Administration

Use **Materi Belajar** in the admin sidebar to create, edit, price, publish, order, or archive videos and online classes. Admin selects the program directly; there is no package/tryout selector.

Migrated legacy records intentionally have a `null` price and are omitted from the public storefront until an administrator reviews and saves an explicit price. This avoids accidentally selling an old bundled item for an inferred or zero price.

## Deployment

1. Back up and verify the target database before deployment.
2. Deploy application assets and PHP source together.
3. Run `php artisan migrate --force`.
4. Run the production asset build used by the hosting environment.
5. Verify member login, catalog filtering, a paid package, a free package, voucher activation, and an online-class link using non-production test accounts where possible.

The separation migration preserves existing rows, backfills material categories from their legacy exam, makes transaction `exam_id` nullable, and adds `learning_material_id`. It also adds separate entitlement indexes plus `grades_exam_user_history_index` for the latest-attempt lookup used when a tryout starts.

Before introducing any future unique constraint on transaction codes or voucher tokens, audit and reconcile existing duplicates. The local development snapshot inspected during this change contained one duplicate transaction-code group and one duplicate non-null voucher-token group, so this change deliberately adds only a non-destructive composite access index.

## Rollback and recovery

Application rollback should be performed first without rolling back the schema. The previous application cannot understand material-target transactions.

The schema rollback deliberately stops when independent materials or material transactions exist. Export those records and restore the pre-migration backup instead of forcing a destructive rollback.

## Current limits

- Videos and meetings are external HTTPS links; media is not uploaded or streamed by this application.
- Payment status still follows the existing transaction administration and voucher workflow.
- WhatsApp delivery remains dependent on the external provider and valid environment configuration. Calls use bounded connect/request timeouts and log transport failures without invalidating an already-created transaction.
- Production migration and deployment require human approval and a verified backup.
